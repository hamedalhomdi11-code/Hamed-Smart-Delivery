# معمارية 6 — الحسابات وتسجيل الدخول | Hamed Smart Delivery

التاريخ: 2026-11-28  
الحالة: **مسودة تأسيسية للنقاش؛ المتطلب الأساسي مسجل، وتفاصيل سياسة الحسابات وآلية المصادقة ما زالت تحتاج اعتماد المستخدم. لم يبدأ التنفيذ البرمجي أو البناء.**

## 1. الهدف الأساسي الذي طلبه المستخدم

يجب ألا يتمكن المستخدم من الدخول إلى التطبيق أو استخدام وظائفه قبل إتمام تسجيل الدخول لأول مرة ببيانات حساب صحيحة.

- عند تشغيل التطبيق لأول مرة، تظهر شاشة البداية ثم شاشة تسجيل الدخول بدلاً من فتح الواجهة التشغيلية.
- لا تظهر وظائف التطبيق الأساسية ولا يمكن تجاوز شاشة الدخول دون مصادقة ناجحة.
- بعد نجاح تسجيل الدخول، يسمح التطبيق بالدخول إلى الواجهة الرئيسية ووظائفه وفق صلاحيات الحساب.
- عند التشغيل اللاحق، تُستعاد الجلسة بشكل آمن إذا كانت لا تزال صالحة، فلا يضطر المستخدم إلى إدخال كلمة المرور في كل مرة.
- إذا انتهت الجلسة أو أُلغي الحساب/الوصول أو سجّل المستخدم الخروج، يعود التطبيق إلى شاشة تسجيل الدخول.
- لا تُعتبر شاشة الدخول بديلاً عن صلاحيات GPS أو الأذونات الأخرى؛ تظل تلك الأذونات تُطلب عند الحاجة وفق سلوك التطبيق.

## 2. سلوك الدخول المقترح — بانتظار اعتماد المستخدم

1. أول تشغيل: شاشة تسجيل دخول إلزامية.
2. إدخال بيانات الحساب والتحقق منها.
3. نجاح المصادقة: فتح التطبيق وحفظ جلسة/رمز وصول آمن قابل للتجديد وفق تصميم الخادم.
4. تشغيل لاحق: فحص صلاحية الجلسة؛ إذا كانت صالحة يُفتح التطبيق، وإذا لم تكن صالحة تظهر شاشة الدخول.
5. تسجيل الخروج: إبطال الجلسة قدر الإمكان من جهة الخادم ومسح بيانات الجلسة المحلية ثم العودة لشاشة الدخول.
6. فشل الاتصال: لا يتم اعتبار المستخدم مسجلاً للدخول لمجرد وجود بيانات مخزنة محلياً؛ تحدد سياسة العمل دون اتصال بعد مناقشتها واعتمادها.

## 3. متطلبات الأمان المبدئية

- عدم تخزين كلمة المرور كنص صريح على الجهاز.
- عدم تضمين كلمات مرور أو مفاتيح سرية ثابتة داخل APK.
- استخدام اتصال مشفر HTTPS عند تبادل بيانات المصادقة.
- حفظ رموز الجلسة في تخزين آمن مناسب لنظام Android، مع تجنب تسجيلها في السجلات.
- التحقق من الحساب والصلاحيات من جهة موثوقة، وعدم الاعتماد على قيمة محلية يستطيع المستخدم تعديلها لتجاوز شاشة الدخول.
- التعامل مع محاولات الدخول الفاشلة وأخطاء الشبكة وانتهاء الجلسة برسائل واضحة.
- تحديد آلية آمنة لاستعادة كلمة المرور أو إعادة تعيينها بعد اعتماد سياسة الحسابات.

هذه مبادئ تصميم أولية وليست تأكيداً بأن خادم مصادقة أو واجهة API موجودة حالياً.

## 4. قرارات لم تُحسم بعد مع المستخدم

يجب عدم افتراض أي خيار من التالي قبل مناقشته:

- هل الحسابات ينشئها المدير/الإدارة مسبقاً ويوزع بياناتها على السائقين، أم يسمح التطبيق بإنشاء حساب ذاتي؟
- هل اسم الدخول رقم جوال، أم اسم مستخدم، أم بريد إلكتروني؟
- هل كلمة المرور مطلوبة مع اسم الدخول؟ وهل يوجد رمز تحقق OTP؟
- هل يوجد نوع واحد من الحسابات أم أدوار مختلفة (سائق، مشرف، مدير)؟
- هل تبقى الجلسة مفتوحة حتى تسجيل الخروج، أم تنتهي بعد مدة محددة؟
- هل يسمح باستخدام محدود دون إنترنت بعد تسجيل دخول سابق، أم يمنع الدخول تماماً عند تعذر التحقق؟
- ما آلية نسيان كلمة المرور/استعادة الحساب؟
- هل الحساب مربوط بجهاز واحد أم يسمح بتسجيله على أكثر من جهاز؟
- هل يحتاج التطبيق إلى موافقة/تفعيل من الإدارة قبل السماح بالدخول؟

## 5. فحص البنية الحالية قبل التنفيذ

قبل كتابة كود المصادقة، يجب فحص المشروع لمعرفة ما إذا كان يحتوي بالفعل على:
- خادم حسابات أو API للمصادقة.
- قاعدة بيانات مستخدمين أو نظام إدارة حسابات.
- إعدادات اتصال أو أسرار بيئة قائمة.
- شاشات دخول أو صلاحيات أو جلسات موجودة.

لا يجوز اختراع عنوان خادم أو افتراض وجود خدمة مصادقة. وإذا لم توجد بنية خلفية مناسبة، تعرض الخيارات على المستخدم قبل إنشاء خادم جديد أو تغيير أي خدمة خارجية.

## 6. التكامل مع المعماريات 4 و5

- معمارية 4: لا تتغير الملاحة أو GPS أو مطابقة الطريق أو التوجيه أو التقدير الاقتصادي بسبب إضافة الحسابات. بعد نجاح الدخول يجب أن تعمل الوظائف القائمة كما هي.
- معمارية 5: تصمم شاشة تسجيل الدخول بنفس الهوية البصرية المعتمدة (كحلي داكن، تركواز/سماوي، أخضر للحالات المناسبة، بطاقات وأزرار متناسقة، وحركة خفيفة)، مع دعم العربية والإنجليزية.
- لا تصغّر مساحة الخريطة بعد الدخول؛ تظل قاعدة معمارية 5 الخاصة بمساحة الخريطة محفوظة.
- لا تُغيّر قاعدة بيانات الرياض أو مخططها أو الخادم الخارجي دون فحص وضرورة وموافقة صريحة من المستخدم.
- نطاق المشروع حصراً Hamed Smart Delivery وليس Hamed Maps.

## 7. التنفيذ والاختبار

بعد حسم القرارات وفحص البنية الحالية:
1. اعتماد مخطط تدفق الدخول والخروج واستعادة الجلسة.
2. اعتماد مصدر المصادقة والـ API قبل ربط التطبيق.
3. تنفيذ حارس دخول (Authentication Gate) يمنع الوصول إلى الشاشات التشغيلية قبل المصادقة.
4. اختبار أول تشغيل، بيانات صحيحة وخاطئة، انقطاع الشبكة، انتهاء الجلسة، تسجيل الخروج، وإعادة تشغيل التطبيق.
5. اختبار عدم إمكانية تجاوز شاشة الدخول عبر الرجوع أو فتح نشاط داخلي مباشرة.
6. اختبار استمرار وظائف GPS والتجمعات والملاحة بعد الدخول.
7. بناء APK فقط بعد موافقة المستخدم الصريحة.

## 8. حالة الاعتماد

المعتمد حالياً فقط: **التطبيق لا يتيح الدخول إلى وظائفه قبل إدخال بيانات تسجيل دخول صحيحة لأول مرة.**

كل ما عدا ذلك في الأقسام 2–7 تصميم مبدئي أو متطلبات فحص واختبار، وتظل الخيارات المحددة في القسم 4 معلقة حتى يقررها المستخدم. لا يعني إنشاء هذه الوثيقة بدء التنفيذ أو البناء.
